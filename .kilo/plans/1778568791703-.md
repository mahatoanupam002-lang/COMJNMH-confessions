# MedReform — Full Production Hardening Plan

## Goal
Transform the current dual-track prototype into a production-ready campus reform platform for COMJNMH: one unified Firebase backend, real authentication, secure admin, anti-abuse protection, working analytics, and a clean repository.

## Current State Snapshot
- **Dual data layer:** `index.html` + `auth.html` use Firebase; `ideas.html` + `submit.html` + `admin.html` use `localStorage` via `data.js`. Data does not flow between them.
- **Firebase placeholders:** `firebase-backend.js` lines 9–14 contain `YOUR_*` literals — `index.html` and `auth.html` will throw on initialization.
- **Hardcoded admin password** in `data.js:8` (`MedReform2025`) — visible to any visitor.
- **Client-only vote dedup** via `localStorage` set in `data.js` — trivial to bypass.
- **Hardcoded GA ID** `G-XXXXXXXXXX` in every page.
- **Dead code:** `comjnmh-ideas.html` (1262 lines), 17 markdown docs in repo root.
- **No tests, no CI, no `package.json`.**

## Phase 2 — Security Hardening

### 2.1 Firestore security rules
Write `firestore.rules`:
- `users/{uid}` — read: signed-in; write: own doc only; `isAdmin` writable only via admin SDK (server-side function or manual console).
- `ideas/{id}` — read: anyone; create: signed-in; update: only `votes`/`voterIds`/`comments`/`flagCount`/`flagged` fields by non-author signed-in users; full update/delete: admin only.
- `flags/{id}` — create: signed-in; read/delete: admin only.

### 2.2 Vote integrity
- Move vote increments into a Firestore transaction (replace current read-modify-write in `MedReformVoting.voteIdea` lines 285-326).
- Cap one vote per `userId` server-side via `voterIds` array membership check inside the transaction.

### 2.3 Rate limiting
- Add a Cloud Function (or Firestore-rules + client throttle) to limit:
  - 5 idea submissions / user / day
  - 30 comments / user / day
  - 10 flags / user / day
- Reject excess on the backend, show toast on client.

### 2.4 Input validation
- Enforce server-side `title.length ≤ 150`, `text.length ≤ 1000`, `comment.text.length ≤ 500` in Firestore rules.
- Sanitize HTML on the server (rules can reject string fields containing `<` or `>`).

### 2.5 Auth hardening
- **Open registration** — any email may register (decided).
- **Email verification required** before submitting, voting, or commenting. Block these actions if `!user.emailVerified`; show "Please verify your email" banner with resend button.
- Send verification email automatically on registration via `user.sendEmailVerification()`.
- Password minimum 10 chars (currently 8).
- Rate-limit registrations per IP (Cloud Function) to prevent verified-email abuse via disposable-mail services.

## Phase 3 — Anti-Abuse & Moderation

### 3.1 Server-side flag thresholds
- Move auto-hide logic from `MedReformFlagging.flagIdea` (line 463) into a Cloud Function trigger on `flags` collection writes — prevents client tampering with `flagCount`.

### 3.2 Profanity / spam filter
- Integrate a lightweight server-side keyword filter on submit (Cloud Function).
- Add a basic Levenshtein duplicate-detection on submit (server-side; current client-side check in `findSimilarIdeas` is bypassable).

### 3.3 Audit log
- New `audit_log` collection: every admin action (status change, delete, flag clear, makeAdmin) writes an entry with `{actorUid, action, targetId, timestamp}`.
- Surface in admin UI as a "Recent Activity" tab.
